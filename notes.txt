3-Layer Architecture:
Split app into 3 parts, each with one job → change one without breaking others 

Presentation Layer: Takes the incoming request and sends back the response — nothing more.
What happens after: It passes the request straight to the Service layer and waits for an answer.
Service Layer: Contains the actual logic — validates input, applies rules, makes decisions.
Then: Based on what the request needs, the service picks the right repository to talk to (e.g., a UserRepository for user data, an OrderRepository for orders).
Repository Layer: Each repository follows an interface — a contract that says "you must implement these methods" (like get(), save(), delete()). Whatever database it uses underneath, it must expose 
these same methods. This repository is the only thing that actually touches the database.

Because the service only talks to the interface, not a specific database, you can swap PostgresUserRepository for MongoUserRepository without changing the service at all — as long as it implements the same methods.

Simple Benefits:

Swap databases without touching business logic
Test logic without needing a real database
Add new features/clients easily — only one layer changes
Easier to find bugs (know exactly which layer to check)
Teams can work on different layers at the same time

-- Dockerfile builds one container. 
Docker Compose connects and runs multiple containers.
Image = frozen template/blueprint. Container = a running instance of that image (like a class vs an object).
Dockerfile = builds one image (recipe for one dish). docker-compose.yml = orchestrates multiple containers together (the whole menu)

-- Docker-compose pattern:
services: lists your containers (e.g. api, db). Each service either build:s from a Dockerfile (your own app) or pulls a premade image: (like postgres:16 — no need to reinvent that). volumes: persist data (like a database's files) outside the container's lifecycle, 
so data survives even if the container is deleted.

-- What to containerize:
Anything that runs as a process (API, database, cache, worker). One container = one job/responsibility — this gives independent scaling, independent 
lifecycles (you change API code constantly, rarely touch DB setup), reuse of existing maintained images, and failure isolation.

Handling heavy traffic:
-- Horizontal scaling = run multiple identical containers of the same stateless image (e.g. FastAPI), with a load balancer (Nginx, cloud LB, Kubernetes) sitting in front deciding which container handles each request. 
Works because FastAPI containers don't hold unique state — Postgres isn't scaled this way by default since copies would mean disconnected data.
-- Vertical scaling = make one container/machine bigger instead. Has a ceiling and no redundancy.
